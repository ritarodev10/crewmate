# Code Conventions

## File naming

| Kind | Pattern | Example |
|---|---|---|
| Module | `kebab.module.ts` | `jobs.module.ts` |
| Controller | `kebab.controller.ts` | `jobs.controller.ts` |
| Service | `kebab.service.ts` | `jobs.service.ts` |
| Repository | `kebab.repository.ts` | `jobs.repository.ts` |
| Resolver | `kebab.resolver.ts` | `jobs.resolver.ts` |
| Gateway | `kebab.gateway.ts` | `jobs.gateway.ts` |
| DTO | `kebab.dto.ts` | `create-job.dto.ts` |
| Event | `kebab.event.ts` | `job-created.event.ts` |
| Guard | `kebab.guard.ts` | `tenant.guard.ts` |
| Interceptor | `kebab.interceptor.ts` | `logging.interceptor.ts` |
| Filter | `kebab.filter.ts` | `prisma-exception.filter.ts` |
| Pipe | `kebab.pipe.ts` | `parse-uuid.pipe.ts` |
| Decorator | `kebab.decorator.ts` | `current-user.decorator.ts` |
| Unit test | `*.spec.ts` colocated | `jobs.service.spec.ts` |
| e2e test | `*.e2e-spec.ts` colocated or in `test/` | `jobs.controller.e2e-spec.ts` |

## Identifier naming

- **Classes**: `PascalCase`. Suffix matches the type. `JobsService`, `CreateJobDto`, `TenantGuard`.
- **Methods, functions, variables**: `camelCase`. Verbs for functions, nouns for values. `createJob`, `pendingJobs`.
- **Constants** with module-wide scope: `SCREAMING_SNAKE_CASE`. `MAX_RETRIES`, `DEFAULT_PAGE_SIZE`.
- **Enums**: `PascalCase` for the type, `SCREAMING_SNAKE_CASE` for members. `JobStatus.IN_PROGRESS`.
- **Boolean variables and methods**: start with `is`, `has`, `should`, `can`. `isCompleted`, `hasWorker`.
- **Async methods** read like statements. `findOneById`, not `getJobAsync`. The fact that it is async lives in the signature.

## Import order

Group with one blank line between groups. ESLint's `import/order` rule enforces this.

```ts
// 1. Node built-ins
import { randomUUID } from 'node:crypto';

// 2. External packages
import { Injectable, Logger } from '@nestjs/common';
import { Prisma } from '@prisma/client';

// 3. Internal absolute (tsconfig paths)
import { PrismaService } from '@core/prisma/prisma.service';
import { TenantContext } from '@shared/context/tenant.context';

// 4. Relative
import { JobsRepository } from './jobs.repository';
import { CreateJobDto } from './dto/create-job.dto';
```

## Code comment formatting

The most important rule. **Comments explain why, not what.** A well-named function does not need a comment to explain what it does.

### When to write a comment

Write a comment only when one of these is true.

- A non-obvious **business rule** is encoded (a regulation, a contract clause, a domain quirk).
- A subtle **invariant** must hold for the code to be correct.
- A **workaround** exists because of a known bug in a dependency, with a link.
- A piece of code looks wrong but is intentional, and a future reader will be tempted to "fix" it.

If a comment would just restate the code, delete it.

### JSDoc on public surfaces

Public services, public methods on shared utilities, and exported types get JSDoc. Controllers and resolvers do not (their decorators and DTOs already document them, plus OpenAPI takes care of the rest).

```ts
/**
 * Transitions a job to the next allowed status.
 *
 * Throws if the transition violates the state machine in
 * job-status.machine.ts. Emits `job.status.changed` on success.
 *
 * @throws {InvalidStatusTransitionException}
 */
async transitionStatus(
  jobId: string,
  next: JobStatus,
  actor: ActorContext,
): Promise<JobResponseDto> { ... }
```

Keep it tight. Three lines is usually enough. Do not document every parameter if the names already say it.

### Inline comments

```ts
// GOOD: explains a non-obvious decision
// We sort by createdAt DESC, then id, to keep ordering stable
// across pages when two jobs share the same timestamp.
const jobs = await this.repository.findManyByTenant({ orderBy: [...] });

// GOOD: pins a workaround
// HACK: Prisma 5.x returns Decimal even when schema says Float.
// Tracking: https://github.com/prisma/prisma/issues/12345
const total = Number(row.total);

// BAD: restates the code
// Increment the counter
counter += 1;
```

### Section banners

Inside long files, banners help, but the better fix is usually to split the file.

```ts
// --- Status machine -----------------------------------------------------
```

Use sparingly. Two per file maximum. If you need more, split.

### TODO, FIXME, HACK markers

```
// TODO(riza, 2026-06-15): pagination cursor when /jobs grows past 10k rows
// FIXME(jobs-1234): race condition on concurrent transitions
// HACK(prisma-12345): workaround for upstream bug, revert when fixed
// NOTE: tenant scoping is applied by TenantGuard, not here
```

Format. `MARKER(owner-or-issue, optional-date): short explanation`. No bare `// TODO` allowed.

### File headers

No file headers. No copyright banners. No "Generated by ..." comments. The file path is the documentation.

## Banned patterns

- `any`, `as any`, `@ts-ignore`, `@ts-nocheck`. Use `unknown` and narrow, or model the type.
- `console.log`, `console.error`. Use the injected `Logger`.
- Default exports. Always named exports.
- Magic numbers and magic strings in business logic. Promote to a named constant or enum.
- `new Date()` inside services. Inject a `ClockService` so tests can fake time.
- Catching an error only to re-throw it.
- Empty `catch` blocks.
- Side effects in constructors. Use `onModuleInit` if initialization is needed.
- `process.env.X` outside `core/config`. Always go through `ConfigService`.
- Inline SQL. Use Prisma. If a raw query is unavoidable, isolate it in the repository and add a comment explaining why.

## Async and error handling

- Always `async/await`. No `.then` chains except inside framework adapters.
- A service method either returns a value or throws. No `{ ok: true, data }` envelopes inside the service layer (envelopes belong to the API contract).
- Validate at the boundary (DTO + ValidationPipe). Inside the service, trust the input shape.
- Map low-level errors (Prisma errors, HTTP errors from external APIs) to domain exceptions at the repository or client layer. The service throws domain exceptions only.

## Logging

- Inject `Logger` per class with the class name. `private readonly logger = new Logger(JobsService.name);`
- Log at the right level. `debug` for development noise, `log` for normal operations, `warn` for recoverable problems, `error` for failures.
- Include structured context. `this.logger.log({ jobId, status }, 'Job transitioned')`.
- Never log secrets, tokens, or full request bodies that may contain PII.
